Dixor.DI Overview & Architecture

Philosophy

In enterprise software engineering, Program.cs and startup files frequently suffer from the "Dependency Registration Dump" anti-pattern:

  • Every time a developer adds an interface and an implementation, they must navigate to Program.cs to add services.AddScoped<IFoo, Foo>();.
  • Merge conflicts in Program.cs are rampant across distributed development teams.
  • Inadvertent lifetime mismatches (e.g., injecting a Scoped service into a Singleton) cause runtime Captive Dependency bugs.

Dixor.DI shifts the responsibility of service lifetime declaration to the implementation class itself using clean, declarative C# attributes.

Service Lifetime Mechanics

Dixor.DI integrates natively with Microsoft's Microsoft.Extensions.DependencyInjection container. It respects the three standard .NET service lifetimes:

graph TD
    A[Container Resolution Request] --> B{Lifetime Attribute}
    B -->|Singleton| C[Single Instance for Entire Application Lifetime]
    B -->|Scoped| D[Single Instance Per HTTP Request / Resolution Scope]
    B -->|Transient| E[Brand New Instance on Every Single Resolution]

1. Singleton ([Singleton])

  • Behavior: Created once on the initial resolution and reused throughout the entire lifespan of the process.
  • Best Used For: In-memory caches, configuration wrappers, stateful thread-safe sequence generators, and computational engines.
  • Example: 
    [Singleton]
public class InMemoryCache : ICacheService
{
    private readonly ConcurrentDictionary<string, object> _cache = new();
}

2. Scoped ([Scoped])

  • Behavior: A distinct instance is created per resolution scope (e.g., per incoming ASP.NET Core HTTP request). All dependencies resolved within the same scope receive the identical instance.
  • Best Used For: Entity Framework Core DbContext repositories, units of work, user context providers, and request audit trackers.
  • Example: 
    [Scoped]
public class OrderRepository : IOrderRepository
{
    private readonly ApplicationDbContext _db;
    public OrderRepository(ApplicationDbContext db) => _db = db;
}

3. Transient ([Transient])

  • Behavior: Instantiated fresh every single time it is requested from the dependency injection container.
  • Best Used For: Lightweight, stateless services, message formatters, calculators, and short-lived algorithmic processors.
  • Example: 
    [Transient]
public class InvoicePdfGenerator : IInvoicePdfGenerator
{
    public byte[] Generate(Order order) { ... }
}

Assembly Scanning Engine

When services.AddDixorServices() or services.AddDixor() is executed:

  1. DixorServiceScanner inspects all public and internal concrete non-abstract classes in the specified assemblies.
  2. It detects classes decorated with [ServiceAttribute] (including derived [Singleton], [Scoped], and [Transient]).
  3. For each detected class:
    • If As is specified, it registers the service against that designated contract type.
    • If As is omitted, it registers the service against all implemented interfaces (excluding system interfaces like IDisposable and IAsyncDisposable).
    • If the class implements no interfaces, it self-registers against its own concrete type.
  4. If Key is specified, it registers as a Keyed Service (IServiceCollection.AddKeyed...).
  5. If TryAdd is true, it uses TryAdd to avoid overriding previously registered implementations.
