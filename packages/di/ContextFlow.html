Ambient Context Flow in Dependency Injection

In complex enterprise applications, passing contextual data—such as TenantId, UserId, CorrelationId, or ClientIp—through every intermediate service in your DI hierarchy leads to Constructor Parameter Pollution (also known as DI "Prop Drilling").

Dixor.DI solves this cleanly with Ambient Context Flow powered by DixorContext and IDixorContextAccessor<TContext>.

The Problem: Constructor Parameter Pollution

Consider a typical 4-tier request handling pipeline:

Controller / Endpoint
       ↓
OrderProcessingService
       ↓
PaymentService
       ↓
AuditLogger & DbRepository

Without ambient context, every single constructor and method signature in the chain must accept tenantId and correlationId:

// ❌ Anti-pattern: Intermediate services are polluted with arguments they only pass down!
public class OrderProcessingService(
    IPaymentService paymentService, 
    string tenantId, 
    string correlationId) // Unneeded by this service!
{
    public void Process() => paymentService.Pay(tenantId, correlationId);
}

public class PaymentService(
    IAuditLogger auditLogger, 
    string tenantId, 
    string correlationId) // Unneeded by this service!
{
    public void Pay(string tenantId, string correlationId) => auditLogger.Log(tenantId, correlationId);
}

This violates the Single Responsibility Principle, breaks encapsulation, complicates unit tests, and creates massive refactoring headaches whenever a new contextual property (e.g. ClientIp) is introduced.

The Solution: Ambient Context Flow

With Dixor.DI, intermediate services have clean constructors. Contextual state flows down the call tree automatically across all async/await boundaries using AsyncLocal<TContext>:

[HTTP Request / Job Entry] -> DixorContext.BeginScope(new RequestContext(...))
                                  ↓
                       OrderProcessingService (Clean constructor!)
                                  ↓
                            PaymentService (Clean constructor!)
                                  ↓
                       AuditLogger (Injects IDixorContextAccessor<RequestContext>)

Step-by-Step Implementation Guide

Step 1: Define Your Context Record or Class

Create a strongly-typed class or record for your ambient context:

public record RequestContext
{
    public required string TenantId { get; init; }
    public required string UserId { get; init; }
    public required string CorrelationId { get; init; }
    public DateTime Timestamp { get; init; } = DateTime.UtcNow;
}

Step 2: Register Dixor Context in Program.cs

Enable context flow in your dependency injection container:

var builder = WebApplication.CreateBuilder(args);

// Register Dixor DI and enable context flow for RequestContext
builder.Services.AddDixor();
builder.Services.AddDixorContext<RequestContext>();

var app = builder.Build();
Note

AddDixorContext<TContext>() registers IDixorContextAccessor<TContext> as a thread-safe singleton backed by AsyncLocal<TContext>.

Step 3: Initialize the Ambient Scope at the Entry Point

Initialize context at your application boundary—such as an ASP.NET Core Middleware, API Filter, or Message Queue Consumer—using DixorContext.BeginScope():

Option A: ASP.NET Core Middleware

public class TenantContextMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext httpContext)
    {
        var tenantId = httpContext.Request.Headers["X-Tenant-Id"].FirstOrDefault() ?? "tenant_default";
        var correlationId = httpContext.Request.Headers["X-Correlation-Id"].FirstOrDefault() 
            ?? Guid.NewGuid().ToString("N");
        var userId = httpContext.User.Identity?.Name ?? "anonymous";

        var context = new RequestContext
        {
            TenantId = tenantId,
            UserId = userId,
            CorrelationId = correlationId
        };

        // Begin ambient scope - automatically flows across all async calls!
        using (DixorContext.BeginScope(context))
        {
            await next(httpContext);
        }
    }
}

// In Program.cs:
app.UseMiddleware<TenantContextMiddleware>();

Option B: Background Worker or Message Queue Consumer

public class OrderQueueConsumer(IOrderService orderService)
{
    public async Task OnMessageReceivedAsync(OrderQueueMessage message)
    {
        var context = new RequestContext
        {
            TenantId = message.TenantId,
            UserId = message.SubmittedBy,
            CorrelationId = message.MessageId
        };

        // Ambient scope cleans up automatically upon disposal
        using (DixorContext.BeginScope(context))
        {
            await orderService.ProcessOrderAsync(message.OrderId);
        }
    }
}

Step 4: Intermediate Services Stay Clean

Notice how OrderProcessingService and PaymentService require zero knowledge of RequestContext or its properties:

[Scoped]
public class OrderProcessingService(IPaymentService paymentService) : IOrderService
{
    public async Task ProcessOrderAsync(string orderId)
    {
        // No tenantId or correlationId passed here!
        await paymentService.ChargeAsync(100.00m);
    }
}

[Scoped]
public class PaymentService(IAuditLogger auditLogger) : IPaymentService
{
    public async Task ChargeAsync(decimal amount)
    {
        // Pure business logic without context plumbing
        await auditLogger.LogActionAsync($"Charged {amount:C}");
    }
}

Step 5: Inject IDixorContextAccessor<T> Directly in Leaf Services

Any leaf component—such as an audit logger, database connection factory, or metrics recorder—injects IDixorContextAccessor<RequestContext> to inspect ambient state:

[Scoped]
public class AuditLogger(
    IDixorContextAccessor<RequestContext> contextAccessor,
    ILogger<AuditLogger> logger) : IAuditLogger
{
    public Task LogActionAsync(string action)
    {
        // Read the ambient context flowed down from the entry point!
        RequestContext? ctx = contextAccessor.Current;

        logger.LogInformation(
            "[{Tenant}] User {User} (Correlation: {Correlation}) executed: {Action}",
            ctx?.TenantId ?? "N/A",
            ctx?.UserId ?? "N/A",
            ctx?.CorrelationId ?? "N/A",
            action);

        return Task.CompletedTask;
    }
}

Comparison: Ambient Context vs Parameterized Factory

Scenario Best Pattern Why?
Cross-Cutting Metadata (Tenant, User, Correlation ID, Locale) Ambient Context Flow (DixorContext + IDixorContextAccessor<T>) Eliminates passing arguments down 5+ intermediate layers. Flow is transparent and automatic.
Object Instantiation with Dynamic Arguments (Worker with orderId, Session with socketId) Parameterized Factory (IDixorFactory<TService, TArg>) Caller explicitly wants to construct a distinct instance using dynamic runtime arguments combined with container dependencies.

Parameterized Factory Example (IDixorFactory<TService, TArg>)

When you specifically need to instantiate a service with runtime parameters:

// Definition:
public class ReportGenerator(
    IDatabaseConnection db, 
    ILogger<ReportGenerator> logger, 
    string reportType)
{
    public void Generate() => logger.LogInformation("Generating {Type}", reportType);
}

// In Program.cs:
builder.Services.AddDixorParameterizedFactory<ReportGenerator, string>();

// In Consumer:
public class ReportController(IDixorFactory<ReportGenerator, string> factory) : ControllerBase
{
    [HttpPost("generate")]
    public IActionResult Generate(string type)
    {
        // DI container supplies db and logger; "type" is passed dynamically at runtime!
        ReportGenerator generator = factory.Create(type);
        generator.Generate();
        return Ok();
    }
}

Safety & Best Practices

  1. Always Use using with BeginScope: Ensures that ambient state is cleaned up when exiting the execution boundary, preventing context leakage between requests.
  2. Contexts Flow Down, Not Up: Child async tasks inherit the parent context. Changes made within an inner scope do not affect outer scopes.
  3. Null-Check Current in Leaf Services: Always gracefully handle cases where code is invoked outside an active context scope (e.g., during background warmup).
