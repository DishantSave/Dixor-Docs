Deterministic One-Way Keyed Hashing (Blind Indexing)

The IDeterministicHasher computes keyed one-way cryptographic hashes (HMAC-SHA256 and HMAC-SHA512) guaranteeing that:

Identical input text with the identical secret key ALWAYS produces the exact same hash output.

This property is the foundation for Blind Indexing in modern secure databases, enabling exact-match search queries on encrypted fields without exposing raw sensitive data.

The Core Challenge: Searching Encrypted Data

When protecting sensitive PII (such as Email Addresses, Social Security Numbers, Phone Numbers, or Bank Account Numbers) in a database, security best practices mandate using authenticated ciphers like AES-256-GCM.

However, AES-256-GCM generates a fresh random 96-bit nonce for every encryption operation. Therefore:

Encrypt("alice@example.com") ──► dx_enc_A8f9e...
Encrypt("alice@example.com") ──► dx_enc_B3c2d... (Completely different!)

Because identical plaintexts yield different ciphertexts, standard database queries fail:

-- ❌ FAILS: Cannot find Alice because her ciphertext changes on every save!
SELECT * FROM Customers WHERE Email = @encryptedEmail;

The Solution: Blind Indexing with IDeterministicHasher

Store two columns in your database table:

  1. EncryptedEmail (Encrypted with IDataEncryptor / AES-256-GCM for confidentiality).
  2. EmailBlindIndex (Hashed with IDeterministicHasher / HMAC-SHA256 for exact-match searching).
                        ┌────────────────────────────────────────────────────────┐
                        │                "alice@example.com"                     │
                        └──────────┬─────────────────────────────┬───────────────┘
                                   │                             │
                   IDataEncryptor.Encrypt()         IDeterministicHasher.HashSha256()
                                   │                             │
                                   ▼                             ▼
                        EncryptedEmail                EmailBlindIndex
                      (dx_enc_A8f9e...)             (9f8a7c6e5b4a3...)

Step-by-Step Implementation Guide

Step 1: Saving a User Record with Blind Indexing

public class UserService(
    IDataEncryptor encryptor,
    IDeterministicHasher hasher,
    IConfiguration config)
{
    private readonly string _aesKey = config["Security:DataKey"]!;
    private readonly string _pepperKey = config["Security:BlindIndexPepper"]!;

    public async Task CreateUserAsync(string email, string fullName)
    {
        // 1. Reversible encrypted data for display to authorized admins:
        string encryptedEmail = encryptor.Encrypt(email, _aesKey);

        // 2. Deterministic one-way hash for database indexing:
        string emailBlindIndex = hasher.HashSha256(email, _pepperKey);

        // 3. Persist to database:
        var user = new UserEntity
        {
            FullName = fullName,
            EncryptedEmail = encryptedEmail,
            EmailBlindIndex = emailBlindIndex // Indexed column in SQL
        };

        await dbContext.Users.AddAsync(user);
        await dbContext.SaveChangesAsync();
    }
}

Step 2: Querying by Email Without Decrypting the Database

When a user searches or logs in by email:

public async Task<UserEntity?> FindByEmailAsync(string email)
{
    // 1. Compute the exact deterministic hash for the search input:
    string searchHash = hasher.HashSha256(email, _pepperKey);

    // 2. Query SQL directly using the indexed column:
    UserEntity? user = await dbContext.Users
        .FirstOrDefaultAsync(u => u.EmailBlindIndex == searchHash);

    return user;
}

Step 3: Verifying Deterministic Hashes

Validate whether a user input matches an expected blind index using constant-time comparison:

bool isMatch = hasher.VerifySha256(
    input: "alice@example.com",
    key: _pepperKey,
    expectedHash: storedBlindIndex);

if (isMatch)
{
    Console.WriteLine("Record matched successfully.");
}

Algorithm Specifications

Method Algorithm Digest Length Recommended Use Case
HashSha256(input, key) HMAC-SHA256 64 lowercase hex characters Standard blind indexing for database columns (Email, SSN, Phone).
HashSha512(input, key) HMAC-SHA512 128 lowercase hex characters Maximum collision resistance for high-volume enterprise identifier tracking.

Security Best Practices for Blind Indexing

  1. Keep the Pepper Secret: The key passed to HashSha256 acts as a secret pepper. Even if an attacker steals your database, they cannot compute rainbow tables or brute-force user emails without your application's pepper key.
  2. Normalize Inputs Prior to Hashing: Email addresses should be trimmed and lowercased (email.Trim().ToLowerInvariant()) before hashing so that "Alice@Example.com" and "alice@example.com" produce matching blind indices.
  3. Never Store Unsalted / Unkeyed MD5 or SHA1: Unkeyed hashes are instantly vulnerable to online rainbow table lookups. Always use IDeterministicHasher with a secure key.
