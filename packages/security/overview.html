Cryptographic Algorithms & Architecture Deep Dive

Dixor.Security is built strictly on modern, NIST-approved, industry-standard cryptographic primitives. This document details each algorithm, its mathematical and operational foundation, its security properties, and how it is applied within the library.

1. Symmetric Encryption: AES-256-GCM (AEAD)

Specification

  • Standard: NIST SP 800-38D (Galois/Counter Mode) / FIPS PUB 197.
  • Key Length: 256 bits (32 bytes).
  • Nonce / IV Length: 96 bits (12 bytes) uniquely generated per encryption.
  • Authentication Tag: 128 bits (16 bytes).

How It Works

AES-GCM is an Authenticated Encryption with Associated Data (AEAD) cipher that provides both Confidentiality (data cannot be read) and Integrity / Authenticity (data cannot be modified or replayed):

Plaintext ───► [ AES Counter Mode (CTR) ] ─────────► Ciphertext
                         │                                │
                     GHASH Over GF(2^128) ◄───────────────┘
                         │
             [ 128-bit Authentication Tag ]
  1. Counter Mode (CTR): An incrementing counter combined with a random 96-bit nonce encrypts data into ciphertext blocks.
  2. GHASH Authenticator: Computes a polynomial evaluation over the Galois field \(GF(2^{128})\) covering the ciphertext and optional Additional Authenticated Data (AAD).
  3. Tamper Rejection: When decrypting, Dixor.Security computes and compares the tag. If a single bit of ciphertext or AAD has been altered, or if the key is incorrect, AesGcm.Decrypt immediately throws a CryptographicException before returning any plaintext, neutralizing padding oracle and chosen-ciphertext attacks.

2. Password Hashing: PBKDF2-HMAC-SHA256

Specification

  • Standard: RFC 2898 / RFC 8018 / NIST SP 800-132.
  • Pseudorandom Function (PRF): HMAC-SHA256.
  • Salt Length: 128 bits (16 bytes) generated via RandomNumberGenerator.
  • Default Iteration Count: 100,000 iterations.
  • Derived Key Length: 256 bits (32 bytes).

How It Works

Standard cryptographic hashes (like SHA-256 or MD5) execute in nanoseconds, making them vulnerable to massive brute-force attacks using GPUs or ASICs. PBKDF2 deliberately introduces computational work:

\(DK = \text{PBKDF2}(\text{HMAC-SHA256}, \text{Password}, \text{Salt}, c = 100000, 32)\)

  1. Unique Salt: Every password hash receives a unique 128-bit random salt, rendering rainbow tables and precomputed hash dictionaries completely ineffective.
  2. Work Factor (\(c\)): The 100,000 iterations force an attacker to compute 100,000 SHA-256 operations for every single guess, raising the cost of offline attacks exponentially while remaining fast (~10ms) for individual user logins.

3. One-Way Keyed Hashing: HMAC-SHA256 & HMAC-SHA512

Specification

  • Standard: RFC 2104 / FIPS PUB 198-1.
  • Hash Functions: SHA-256 (64 hex characters) and SHA-512 (128 hex characters).

How It Works

HMAC applies a cryptographic hash function in a nested structure with an application secret key:

\(\text{HMAC}(K, m) = H((K' \oplus opad) \parallel H((K' \oplus ipad) \parallel m))\)

Where \(ipad\) and \(opad\) are inner and outer padding constants.

The Problem of Blind Indexing

When encrypting sensitive database columns (e.g. Email or SSN) with AES-256-GCM, the 96-bit random nonce ensures that encrypting "user@dixor.io" twice produces two completely different ciphertexts. This makes SQL queries like WHERE Email = @val impossible.

The Solution: Deterministic Keyed Hashing

IDeterministicHasher computes an HMAC over the plaintext using a secret pepper. Because HMAC is deterministic for a given key:

  1. "user@dixor.io" + SecretKey \(\implies\) always produces the exact same 64-character hash digest.
  2. Without SecretKey, an attacker obtaining database dumps cannot match hashes against rainbow tables.
  3. You can safely execute exact-match queries: 
    SELECT * FROM Users WHERE EmailHash = @computedHash;

4. Asymmetric Authentication: RSA & ECDSA

Specification

  • RSA: 2048-bit or 4096-bit keys with PKCS#1 v1.5 padding and SHA-256 (FIPS 186-4).
  • ECDSA: NIST P-256 curve (secp256r1) with SHA-256 (RFC 5480 / FIPS 186-4).
  • PEM Format: RFC 7468 (PKCS#8 Private Key, SubjectPublicKeyInfo Public Key).

How It Works

  • RSA: Relies on the mathematical difficulty of factoring the product of two large prime numbers (\(n = p \times q\)).
  • ECDSA: Relies on the elliptic curve discrete logarithm problem over the prime field \(y^2 = x^3 - 3x + b \pmod p\). Provides equivalent security to RSA-3072 with smaller key sizes (256 bits) and higher signing throughput.
  • Verification: The signer signs the SHA-256 hash of the payload using their Private Key; any verifying party verifies the signature using the Public Key without ever possessing the private signing key.

5. Two-Factor Authentication: TOTP (RFC 6238)

Specification

  • Standard: RFC 6238 (Time-Based One-Time Password Algorithm) & RFC 4226 (HOTP).
  • Base32 Alphabet: RFC 4648 (A-Z, 2-7).
  • Time Step: 30 seconds.
  • HMAC Function: HMAC-SHA1 (universal standard for Google and Microsoft Authenticator).

How It Works

  1. Time Counter: Calculates \(T = \lfloor \frac{\text{unixTime}}{30} \rfloor\).
  2. HMAC Computation: Computes \(\text{HMAC-SHA1}(Key_{Base32}, T_{8-byte})\).
  3. Dynamic Truncation: Extracts a 4-byte dynamic binary code based on the offset stored in the lower 4 bits of the last hash byte: \(\text{offset} = \text{hash}[19] \ \& \ 0x0F\) \(\text{code} = (\text{binaryExtract} \pmod{10^6})\)
  4. Clock Drift Tolerance: Validates passcodes at \(T\), \(T-1\), and \(T+1\) to ensure user authentication succeeds even if the client's phone clock is up to 30 seconds out of sync with the server.

6. Side-Channel Defense: Constant-Time Comparisons

The Timing Attack Vulnerability

Standard string and array equality operators (==, string.Equals()) compare characters sequentially and return false on the first non-matching byte:

// ❌ VULNERABLE TO TIMING ATTACKS:
bool CheckToken(string supplied, string expected)
{
    // Returns immediately if first character fails (fast).
    // Returns after 31 characters if 31st fails (slower).
    // An attacker measuring network response latency in microseconds can deduce the secret character by character!
    return supplied == expected; 
}

The Fix

CryptographicUtils.FixedTimeEquals and Dixor.Security services compare every single byte across the entire buffer regardless of where mismatches occur, ensuring constant execution time:

// ✅ SECURE:
CryptographicOperations.FixedTimeEquals(suppliedBytes, expectedBytes);

All secret comparisons, password validations, API key verifications, and token signatures in Dixor.Security are strictly timing-safe.
